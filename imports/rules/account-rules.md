For PayPal, do not rely only on the sign of Gross, because PayPal exports include real payments, income, temporary holds, reversals, and internal balance movements. First, ignore or separately flag rows with Status = Pending, because these are not final transactions yet. Use Status = Completed as the main valid set. Use Type, Name, Balance Impact, and Transaction Event Code together to classify the row. Sales income usually appears as positive Net / positive balance impact, where the payer is a customer and the row type is something like Express Checkout Payment. Vendor expenses usually appear as negative Net / debit balance impact, such as PreApproved Payment Bill User Payment, where Name is the merchant (for example Uber, Libsyn, Superprof). “Account Hold for Open Authorization” is not a real final expense, just a temporary authorization hold, so it should not be treated as a completed transaction. “Reversal of General Account Hold” is also not real income, just the release of that hold, and it should be linked back to the original hold through Reference Txn ID or Original Invoice ID and cancelled out. Use Net as the final amount in account currency, store Gross and Fee separately, and use Currency as the transaction currency. Vendor or client name should come from Name, item or product can come from Item Title, and transaction_id should be the unique external ID. In short: normalize only completed real payments, treat holds and reversals as paired temporary events, use Net as the effective amount, and classify direction by actual business meaning, not just by sign.

Each section includes a card identifier (Mastercard or Visa MAX), which should be used to map transactions to the correct account. Vendor should be taken from the business/merchant name field. Since the file structure is inconsistent (multiple headers and sections), parsing must rely on detecting valid rows rather than fixed positions.

Regarding upload: it’s better to process the Excel file directly (not split into CSVs), so you can preserve sheet structure (ILS vs USD) and detect multiple card sections correctly in one pass.

In most cases all transactions are expenses, so negative amounts = direction out, and if any positive values appear they should be treated as direction in. Currency is always EUR.

The Description field is the main source of truth and should be parsed. It usually starts with a payment type (e.g. “PAGO MOVIL” = mobile/contactless payment, “BIZUM” = peer-to-peer transfer), followed by the merchant name, then location (after a comma), and sometimes ends with a masked card reference. Vendor name should be extracted from the description (typically the first meaningful name after the payment type). All classification (type, vendor, possible category) should be derived from Description, since there are no structured fields for this. Overall, Santander requires more text parsing compared to other sources, but the structure is consistent enough to rely on Description as the primary field.
